## 一、总评

**思路成立，且不是外来物种。** 方案的三个核心机制与本仓三条现役纪律严格同构：

| 方案机制 | 仓库现役同构物 | 判定 |
|---|---|---|
| 分数即推荐，不写"推荐"二字，永不替作家做决定 | v5.0「证据即收据、不裁决」+ 阈值清剿口径（2026-09-24 人裁：数值线不构成打回循环） | 同构，方向被本仓验证半年 |
| ask_user 三触发（分数接近/不可逆分叉/伏笔未回收） | Jev 调研启示#2「低置信升级人审」+ R8⑧「调研能定的不逼人开口」 | 同构，且 R8⑧ 已有落地形态（required:false 先验） |
| 点击选择带证据记账（上下文+选项+分数+实际选择） | R8③ 决策必须带 by + evidence | 点击流天然就是 decision 记账格式 |

但方案有**三处硬伤需要修正**（证据见 §三），其中一处（Step 2 打分底座）直接决定 MVP 形态：

1. **Step 2 写的"Jev（semif backend）"在盘上已不存在**——semif 4B 运行时（GGUF+venv+daemon）已于 2026-09-24 人裁卸载。
2. **Jev 是外部商业产品**（TypeSafe AI，2026-09 发布），不是本仓组件——把它写进自研技术栈表 = 立项即外挂依赖，且稿件会出本机。
3. **打分形态选错了**：本仓 09-23 两次实测（§三.3）不支持"快 logprob 引擎打剧情分"，支持的是同模型 chat+JSON 批判。

**一句话工程路线**：交互面板 + 四象限生成 + chat+JSON 打分起步（API 或本地模型均可）→ 点击流攒校准卷 → 本地 4B 复原后换装 typed 打分（对照校准卷裁决）→ laya-ft 管线蒸馏学生头。交互范式（本方案真正的产品赌注）在 Phase 1 就能完整验证，不被打分底座阻塞。

## 三、三处硬修正（证据）

### 1. Step 2 打分底座空位——"semif backend"已不在盘上

- `tools/_vendor/README.md` L13-21：SemIf/（.venv+GGUF 约 1.4GB）连同 `tools/semif-scan.py`、`tools/semif-daemon/`、`tools/semif-mcp/` 于 2026-09-24 一并卸载；复原路径 = 按 `knowledge/semif-calibration/index.json` modelPins 钉版（GGUF sha256 前缀 **13c16f426047**）重新克隆+建 venv+放模型。
- 方案写"Qwen3.5-4B GGUF（已下载）"——**盘上快速核查未见**（vendor 已清，D 盘浅层无 GGUF）。被卸载的那个 1.4GB GGUF 正是冻结 Qwen3.5-4B（dash-abuse 报告口径：「SemIf 直评（冻结 Qwen3.5-4B typed-logit，纯 CPU）」）。若另行存有副本，复原前先对 sha256 前缀验明正身。
- 影响：方案延迟预算里"Step 2 打分 ~300ms（一次 prefill 16 判定）"对应的 typed-logit 形态**当前不可用**，且该形态在叙事质量维度（区别于文本违规条款）的有效性**无任何实验支撑**——待测。

### 2. Jev 身份误记——它是外部厂商产品，不是"semif backend"

- 《调研-Jev与SystemOne决策层-20260923.md》：Jev = TypeSafe AI 的「System One 模型」，性能数字（193.6x/444.6x）为**厂商口径未独立验证**；第三方实测一致率 **67.8%**——调研原文判读：「恰好印证 System One 不能当闸」。
- 该调研建议动作#5 的边界至今有效：「评估以接口形状可借鉴为限，不追平台绑定」。
- 修正方案：**采纳它的接口形状，不采纳它的产品**——打分器对外暴露 typed decision 协议 `{decision, confidence, reason}` + 低置信升级路径（即 ask_user），实现自研。若 Jev API 未来可用，按调研建议动作#4 跑一组「自研判官 vs Jev」对照校准卷再议，不做立项依赖（作家稿件出本机是产品级问题，本地优先应为默认）。

### 3. 打分形态选错——本仓自己的实验已经投过票

两次实测，结论一致：

**实验 A（dash-abuse 19 题金标卷，09-23）**：4B semif 15/19=79% vs Laya choice 10/19=53% / noul 6/18=33%；laya 否定类合法样张 7/8 高置信误判（p_yes 0.69-0.96）。结论原文：「判官不换……System One 通用检查点在领域语料上的边界判断不可信，必须领域校准」。

**实验 B（剧情路线 choice 对照，09-23，`docs/实验-剧情路线choice对照-20260923.md`）**——这就是本方案核心环路的雏形：
- 4B（**chat+JSON**，daemon 常驻）四轮轨迹连贯且贴人设（把柄→赌约→交底→合流，全在"账"的语汇里，与林寻人设严丝合缝）；
- Laya（快 logprob 原语）置信度全崩（0.000~0.064），三轮押同一极端项且给不出理由；
- **随机基线蒙对 3/4**——观察 3 原文：「候选路线的趣味差要成立，出题人得故意把保守项写得更诱人，本轮没做到位」。

推论：
1. 剧情判断这个任务形态，**chat+JSON 批判（同底座一次调用出 4 选项×4 维结构化评分）是已被验证可用的形态**，延迟 +1-2s/拍，在方案 3-5s 预算内；
2. 快 logprob 引擎打剧情分**已被证伪一次**，换装 typed-logit 属 Phase 4 优化，且必须过对照校准卷；
3. 四象限配额方向正确，但要补一条：**同质化不是唯一敌人，"凑数陪跑项"同样让分数失去意义**——生成指令里每个象限选项必须"写得诱人"（含保守项），MVP 验收应测**分数区分度**而非"能出分"。

## 四、与 09-24 人裁的关系（适用边界，先说清楚再动手）

人裁《laya唯一引擎-20260924》生效范围 = **条款批扫/判官粗筛/一切机器筛选路径**（质量闸位）；「没有4b兜底，never」禁的是 4B 在质量扫描路径冒充闸。

本引擎不在此射程内，因为：打分输出 = 排序建议 + 分数标注，**作家每拍终裁**——这正是 skillrouter 建议面语义（排序建议不裁决）。4B/本地轻模型在这里的角色 = 建议面引擎，不是闸。

但要防两种越界，写进设计约束：

1. **打分结果不得回流为提交闸**：任何「OOC>0.3 禁止采纳/提交」形态的规则 = 断言协议复活，违反 v5.0 退役令与阈值清剿口径。分数永远只排序、只标注、只进复核清单。
2. **known-weakness 如实随件**：未过校准卷的维度打分带 `pilot` 标签进面板（同 laya 学生 dash 0.474 随件带标签的先例），不装可信。
3. **模型档位纪律的类推**：四维打分是文学判断，轻模型默默跑视同虚报。缓解：面板标注打分引擎身份 + 模型 pin + 每维三态（calibrated/pilot）；强模型档的终裁权在作家手里。

## 六、MVP 重排（对方案 Phase 1-4 的修正）

**Phase 1'（单拍闭环，1-2 周）**——原方案骨架保留，打分换形态：
- 剧本/角色卡 schema + contracts
- 四象限生成（chat，先 API 强模型或本地模型皆可——**本地化是省钱优化，不是正确性依赖**）
- 打分 = 同底座 chat+JSON 一次批判（4 选项×4 维结构化输出），typed decision 接口
- CLI/最简面板：选项+分数 → 点击 → 下一拍
- 验收（建议口径，**待拍板，本稿不自行设闸**）：12 拍一场戏每拍 4 选项出齐、四象限覆盖、Top1-Top2 分差可辨；人裁记账项：作家盲选与引擎 Top1 一致率、回退率——只记账，不设线

**Phase 2'（场景级，2-3 周）**：拍循环状态机 + 状态传递、ask_user 三触发（阈值初值进 config 旋钮表并标 pilot，从点击流数据回来后再校准）、回退/分叉预览（3 拍上限、未选分支归档）、前端落 storyharness 门面。

**Phase 3'（作品级，3-4 周）**：弧线/伏笔对齐既有 op 格式；场景草稿生成；**四维各建金标卷**（19-22 题级，金标 = 作家自己的历史选择，套 semif-calibration 三态纪律 + modelPins：换模型或改题面 = 该卷作废重体检）。

**Phase 4'（自优化）**：统计校准 → few-shot 注入 → 复原本地 4B 跑「chat+JSON vs typed-logit vs Jev API」对照校准卷换装 → laya-ft 管线蒸馏叙事打分学生头（GSS K=5 软标签，教师 = 强模型 API，金标 = 作家点击流）。

## 七、风险补遗（原方案八条之外，仓库特有）

| 风险 | 对策 |
|---|---|

| 稿件出本机 | API/Jev 外部判官属 outward 动作，产品默认本地优先；接外部前显式征得作家同意 |
| R8 选择语义混入 | 场景前提若含 enum 类输入（叙事路线表态等），禁 default、开跑显式表态；「自由发挥」象限是显式生成物，不算静默兜底 |

原方案八条风险里，本仓视角下评价：四象限+温度+意外保底（同质化）、冻结基准集回归（打分漂移）、「自己写」一键可达（作家手感）——三条直接成立；剧情树爆炸（预览限 3 拍+24h 归档）与长上下文分层摘要——成立且分别与分叉纪律、节卷积滚上下文纪律同构。

## 附：方案中不需要改的部分（一句话带过）

三操作体验定义（点选/答追问/改文本）、composite 按弧线位置加权（进 config）、回退秒级靠上下文缓存、分叉预览限 3 拍、润色 diff 回传闭环（台词风格 diff 喂 speech_pattern、结构 diff 喂权重）——设计均成立，其中反馈闭环与 laya-ft 标注管线天然衔接，是本方案最有长期价值的部分。

本质定位（供对话引用）：方案把 galgame 写死的可能性树实时化给作家修剪——这与 09-23 调研启示#4「LLM 规划、判官决策」的分层是同一个形式化：**作家 = System 2，引擎 = System 1，ask_user = 低置信升级人审**。本仓已有的纪律资产（校准三态、建议面不裁决、R8 选择记账）恰好是这套产品最缺的地基，双方互为拼图。
