### 铁证：一条 `status: applied` 却从未被读取的 patch

`projects/ccwd-fq/registry/overlay.json` 有 2 条 `set-tool`，`"status": "applied"`，history 记 `actor:"user"`（2026-09-18 拍板落地）：

## 二 · 可调面总表（「能不能调」不再取决于常数写在哪一层）

分三层，**规则统一**：出厂默认 → 项目覆盖 → 节点/op 覆盖。**任一层都不许把默认值写死在代码里读不到的地方。**

### A · 已可调（现状，无需改造）

`op.config` 声明式旋钮（`resolveToolConfig`，`kits.ts:277`）：`depth` / `strictness` / `maxChars` / `model_tier`，
以及模块级专属项（`chapterMin`/`chapterMax`/`minScenes`/`passes`/`innerLoops`/`deadlineRounds`/`scale` 等）。
合成优先级：**`overlay.opConfig` > 节点 `config` > `op.default` > 通用默认**（`overlay.ts` 路径）；
`unknownKeys` 显式回显，不静默丢弃。

### B · 本波新增（OS-02 阶段 A 已接线，2026-09-20）

| 字段 | 位置 | 出厂默认 | 作用 | 落地 |
|---|---|---|---|---|
| `policy.maxRounds` | `flow.schema.json` `policy` | 不设上限（旧行为） | 单个 link 累计驳回上限；超限 → `blocked`（**停机等人，不再无限乒乓**） | `kernel.ts::doGate` link 分支 + `rejectCapped` |
| `policy.awaitTimeoutMs` | 同上 | 不设超时 | 等待态最长毫秒；到点 → `status=blocked` + `stalledAt`（**只标记不自动推进**） | `kernel.ts::markStalled`（`advance` 入口） |

两者对 **flow@2 / flow@3 同等生效**：`effectiveFlow` 此前只透传
`kit_boundary/gate_mode/adapt/budget`，`maxRounds`/`awaitTimeoutMs` 会被静默丢掉；
本批一并补上（flow@3 侧在 `POLICY_KEYS` 白名单里，早已透传）。

> 顺带解释了「`itb-` 门为什么能拦住人」之外的第二种失控：**连接件驳回没有上限**，
> 「驳回 → 重跑上游 → 再撞同一门 → 再驳回」可以无限循环，只有人肉盯得住。

| `pkg.budget.maxContextChars` | 35000 | `assembler.ts:388` |

### 勘误 2：默认值语义不一致（**待 OS-02 拍板**）

| 声明处 | 说法 |
|---|---|
| `contracts/module.schema.json`（本波已保留此措辞） | 「**缺省不声明 = 无档位约束**」 |
| `core/src/kits.ts:249-253`（引擎） | `default: "high"`，且 `resolveToolConfig:288` **会回填** |

### 新发现（执行中实测，均已记入工单）

**N1 · `state.plan` 是陈旧快照，且 `replan()` 从未运行过 —— 最高严重度**

| 实测 | 值 |
|---|---|
| `projects/*/state.json` 的 `state.planHash` | **11/11 全部缺失**（`None`） |
| `state.plan.order` 里的 `itb-` 节点 | **11/11 全部有**（2–3 个） |
| `projects/*/registry/effective.json` 的 `itb-` 节点 | **0/11**（一个都没有） |

`kernel.ts:823 let order = state.plan?.order ?? compilePlan(...)` ⇒ **计划只要存在就照用**；
而 `replan()`（`kernel.ts:1097`）会写 `state.planHash` —— 它从未被写过，**说明 replan 从未运行**。
⇒ 调度器走的 `order` 里含**当前生效编排中根本不存在**的节点（`itb-*`）。
这正是审计 §一.5「overlayHash 漂移不 replan，静默沿用旧快照」的**实体证据**，
也解释了「铁律 6 人工只在边界」为何在 R6 之后仍被 `itb-` 门实际拦截（`p-wxl-001` 04:41 的 reject 正是 `itb-m4.export-doc`）。
**处置**：属 OS-02 阶段 A（`kernel.ts`，需谨慎，涉存量 run 状态）——**本批未动**。

**N2 · `adapt: "off"` 与 `"propose"` 行为等价 —— 「只观测」语义未实现**

`optimize.ts:329` 唯一的判断是 `adapt === "apply" && p.risk === "low" && !isStructuralPatch(p.patch)`。
⇒ 声明 `off`（只观测）与 `propose`（只出提案）**产出完全相同**。`flow@3` 两条流都声明 `adapt:"off"`，
而存量 11 个项目的 `effective.json` 全是 `adapt:"propose"`（因为此前 policy 被忽略）。
**处置**：实现 `off` 的语义（不产出提案）或从契约删除该取值 —— **需人拍板**（改变优化器可观测行为）。

**N3 · `R7` 编号在本仓有歧义**

`R7` 既是**规范版本号**（`规范-…-R5.md`/`-R6.md`/本文件 `-R7.md`），又是**优化器规则号**
（`optimize.ts` 内 `R3-tier-up` / `R6-autogate-cleanup` / `R7-boundary-auto` / `R9-hot-depth`）。
两者是不同命名空间却共用 `R<n>`。**建议**：后续规范改用 `R7-spec` 或直接换主题词，避免与规则号撞车。

**N4 · `R7-boundary-auto` 产出的 patch 在 flow@3 被显式忽略**

`optimize.ts:240-256` 产 `set-policy {key:"kit_boundary", value:"auto"}`。
`kit_boundary` 在 R6 已退役（`types.ts:117`），本规范 §一 也已把它移出 flow@3 白名单 ⇒
**该 patch 在 flow@3 上被显式列进 `unsupported`**（不再静默）。
**根因**：R6 退役了 kit 边界，却**没有提供 per-link 的替代**——现有 kind 里没有 `set-link`，
`sorted link_default` 是全局的，无法表达「只把某一处边界降为 auto」。
**处置**：新增 `set-link {link:<实例id>, mode:"auto"|"manual"}` 契约，或明确删除该规则 —— **需人拍板**。

| `blocked` | **停机等人**（重跑超限 / 等待超时 / 源文件缺失） | `flow_resume`（清停机标记 + 按因重跑） |
| `completed` | 终态 | — |
| `failed` | 终态（门 reject） | `flow_resume` / `flow_rerun` |

**恢复语义的一条纪律**：`blocked` 的两种成因必须分开——**被打回**（上游不合格 ⇒ 重跑上游）
与**等待超时**（上游无辜 ⇒ 只澄清标记、**保留**已验收成果、等待计时重起）。
把「等太久」也当驳回去清上游，不是恢复，是破坏。

### 新发现（N5–N7）

**N5 · `kit_boundary="auto"` 结构性损坏 —— 一条从未被跑到、且会截断整个流程的能力（P0）**

旧实现给 `auto` 的边界门挂节点级 `when:{input:"__boundary_auto__", eq:"never"}`，
而 `plan.ts:52` 会把不活跃节点的**出入边一并裁掉**：

```
itb-structure 被判不活跃 → e-struct 与 e-itb-structure-out 一起消失
→ structure 只剩「全量前向入边」里的 itb-structure（非 0 入度）⇒ 不是源点
→ structure 不可达 → 其后全部不可达 → 计划在门处截断 → advance 无节点可推进 ⇒ run 判 completed
```

实测（`tests` 夹具，`topic-selection`）：`plan.order` 止于 `gate-r1`（**8** 节点，应为 **22**），
一半节点 `status` 停在 `none`，而 `state.status = completed`。
**为何一直没暴露**：出厂缺省是 `always`（走不到 `auto` 分支），而 `optimize.ts:240-256` 恰恰把
`kit_boundary → auto` 当**低风险提案自动落地** —— 等于优化器一动手就截断流程。
**修法**：不再用节点级 `when` 关边界门，改为**留在计划内、由 `advance` 自动裁决**
（`kernel.ts` gate 分支新增 `boundary && kit_boundary==="auto"` 的 auto-pass，指标照记 `boundary` 相）。
**守规矩的守卫**：`r7-runtime.test.ts` 新增「真实 flow@3 计划不得在连接件/边界门处截断」
（除显式 `when` 外，图中节点与计划节点一一对应）。
