## 一 · 逐项落地

### D1 · flow_submit 合并 dispatch 标尺卡进 ctx.ids ✅

**病根（两处，不是一个）**

1. **id 空间不一致**：dispatch 相记的是 `pkg.knowledge[].id`（glob 已展开、预算已裁的**精确**卡 id）+ `pkg.context[].ref`；而 `doSubmit` 用的是 `opRef.knowledge`（op **声明的原始**清单）+ 上游文件路径。于是 `kb/trope/*` 以**通配符字面量**占着分子位、永不可能命中 → 标尺卡命中率被系统性压到 0。_918test 实证：梗卡明明在头部与正文引用了 5 张，计数仍是 0。
2. **分母双计**：`metrics.ts` 的 `kbOffered` 对**所有**事件的 `ctx.ids` 计数，dispatch / submit 各记一次 → 同一 id 分母 ×2。

**改法**
- `core/src/kernel.ts::doSubmit` — 提取清单改为重算任务包，取与派发**完全同源**的那份：
  ```ts
  const pkg = buildTaskPackage(projectDir, flow, state, nodeId, eff.toolOverrides);
  const injected = [...(pkg.knowledge ?? []).map((k) => k.id), ...pkg.context.map((c) => c.ref)];
  ```
  （包在原有 `try{}catch{}` 里——指标是旁路，任何异常都不许阻断流水线。）
- `core/src/metrics.ts::summarizeMetrics` — 分母只在 `phase === "dispatch"` 计数，分子取任何带 `hitIds` 的事件。

**证据**：`core/test/caliber.test.ts` 断言 dispatch+submit 双事件下 `offered === 1`（不是 2）、`hitRate === 1`。

### D2 · enum input 支持 config 绑定 ✅

**病根**：`configToInputs` 只认 `风格`/`AB测试` 两个字段做**推导**，配置文件里直接写的 `route: "dual"` 被整条忽略 → enum 输入永远落回 flow 默认值。_918test 实证：两份 `项目配置.json` 都写了 `route: dual`，`state.inputs.route` 却落在 `"hot"`，于是 `when: {input: route, eq: dual}` 的**「双版本对照」支线两条线都没激活**——设计成了声明的谎言。

**改法**（`core/src/project-config.ts`）
1. **直通**：配置里与 flow 输入**同名**的键原样透传（enum / string / number / boolean 都吃）；
2. enum 取值不在 `options` 内 → **开跑前大声失败**（静默回落才是最难查的）；
3. **推导**降为回退：仅当直通没给 `route` 时才由 `AB测试` > `风格` 推。

**证据**：`core/test/config.test.ts` 新增 2 条——纯函数优先级（直通 > 推导 > 默认）＋ **端到端**（真跑 `flow_run`，配置写 `route: dual` → `state.inputs.route === "dual"`，此前是 `"hot"`）。

> 顺带说明：报告 §一.3 提到的 `episode-script` 里 `route` 默认 `hot` 也一并受益——现在项目配置能压过它。

### D3 · audit 前置进 chapter 循环 ⚠️ 前提已不成立（未改代码）

**核实结果**：报告写这条时的前提是「断言要到三章写完才跑」。但在 `f424b33` 上实测：

- `kits/prose/kit.json` 的 `novel-chapter` **已经声明** `AE-PROSE-TRIPLET / NOTBUT / RHYTHM / SLOP` + `AE-WNF-HOOK` 等 12 条；
- `core/src/aesthetic.ts:155` **已经实现** `AE-WNF-HOOK` 的机器校验器（章末钩 + 四型轮换）；
- `kernel.doSubmit` 在**批式提前返回之前**（`batchable && !seal` 的 return 在断言之前）就跑 `runDeclaredAsserts` ——**逐章提交即逐章断言**。

即：R5 §4.1「声明的断言必须被执行」的收口（2026-09-17 夜）已经让这条**在机制上成立**，无需改 flow 结构。`audit`（core 节点）现在的增量价值只剩「引擎**全量**扫描 + 收据落盘」，不再是唯一的反馈入口。

**残留**：若要 `audit` 的引擎全量扫描也逐章（而非三章后一次），需要让 `audit` 与 `chapter` 同 `iterate` —— 那是**改图的形状**，属 v3 的模块/插槽语义，建议留给 `WO批次-模块化flow-v3`。**本批不动。**

### D4 · find-trope / plot-redline 注入收窄 ⚠️ 部分落地

**已做（find-trope）**：`kits/search/kit.json` 加 `exclude_knowledge` 剔除 3 张**北美市场**梗卡
（`na-billionaire` / `na-fantasy` / `na-werewolf`）。理据不是"让数字好看"，而是语义：flow 自带 `region` 输入（默认 `CN`），NA 梗族对 CN 项目是纯噪声。13 → 10。
- 用 `exclude_knowledge`（精确、可审计、可回滚）而非改 glob —— NA 项目可用 overlay `set-tool add_knowledge` 加回。
- 装载侧会把它们显式回显为「已剔除条款」，**不静默消失**（`loadKnowledge` 的既有行为）。

**未做（plot-redline）**：它的病是 **5 道门共用一份 7 卡的全量注入清单**（offered 28–58 / used 5–6）。要在 flow@2 里"按门裁剪"是不可能的——`knowledge` 挂在 **op 级**，而每个门节点共享同一个 op。R4 恰恰**刻意**删掉了节点级知识字段（避免第二处真相）。⇒ 正解是 v3 的**模块插槽 + 按连接件收窄注入**，属 `WO-01`/`WO-03` 范围。

**为什么不再往下收窄**：`≤5 张` 这个目标值只有在 **D1 修好之后**才可验证——在此之前"哪些卡是死条款"根本测不准。现在 D1 已落地，收窄应当走 R5 设计的证据路径：`flow_effect` 出真实逐卡命中率 → 优化器提 `set-tool remove_knowledge` 提案 → 人批（报告里的 P2/P3 正是这个意思）。

### D5 · headerTemplate 附正文骨架 + 任务包下发禁词表 ✅

**病根**：`headerTemplate` 只渲染 YAML 头，正文格式靠**交卷后**的断言兜——而头部断言要求「正文首行须为一级标题」「标题后须紧接一行 `> 摘要`」，没给骨架就是**让写手猜**。_918test 里这是**最大单源打回（5+ 次）**；另有 glossary 打回 2 次（`老周`/`思维链`/`魏峥`——**全是别的项目的专名**，写手事前无从得知）。

**改法**
1. `core/src/asserts.ts` 新增 `bodySkeleton(cls)`，产出与头部断言**逐字一致**的正文骨架：
   ```
   # <标题>
   > <一句话摘要，≤60 字，不得复述标题>
   ```
   `headerTemplate` 增可选 `skeleton` 参数，附在闭合 `---` **之后**（不污染 YAML 头）。
2. `core/src/asserts.ts` 新增 `foreignOwnTerms(root, projectDir)`：他项目 `词汇表.json` 的 `own` 词投影（保留「本项目 own 词包含则豁免」规则）。`checkGlossary` 一并重构到同一份 `readProjectOwn` 上——**交卷后的断言与开跑前的禁词表同源**，不另起一套。
3. `core/src/assembler.ts::buildTaskPackage` 注入 `## 禁词表（…出现即 glossary 断言打回）` 段 + 给 `headerTemplate` 传骨架。

**证据**：`core/test/caliber.test.ts` 断言骨架落在头之后、头部区间内不出现骨架、不传 `skeleton` 时行为不变；并用**真实数据**断言 `foreignOwnTerms(p-fq-001)` 含 `老周`/`魏峥`、不含本项目 own 词 `陈潮生`、且已去重。
