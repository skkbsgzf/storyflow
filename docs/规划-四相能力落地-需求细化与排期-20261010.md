## 二 · 四需求细化

### 需求 1 · 项目本地文件体系（每个项目 = 独立文风/规则/校验标准）

**目标**：kit 提供模板与范式，不概括；项目文件体系可初始化、可索引、可增量、可 RAG 化，全程本地。

| # | 能力 | 现状锚点 | 要做什么 |
| --- | --- | --- | --- |
| 1.1 | 初始化与索引 | project-init.py 只建骨架 | 路径探索 → `project-index.json`；角色标注（人写/生成物）首次交互问一次，不纯 AI 猜 |
| 1.2 | 增量更新 | 无 | 定期/触发式 diff；生成物 vs 手写物区分标记；手改文件后索引正确失效，索引不污染源文件 |
| 1.3 | 记忆本地化 | 会话 JSONL 在 `projects/<id>/` | JSONL → 人机双读的项目记忆卡 |
| 1.4 | 阶段 RAG 化 | kit-compile.py 只编全局 knowledge/ | 项目创作内容 → **项目级** rag 包；与全局 `kit/` 严格隔离（项目内容不进全局 KB）；kb 检索双根合并（全局+项目） |

- **契约依赖**：`contracts/project-index.schema.json`（W2 开头出，契约先行）。
- **决策点 D1**：项目根口径。推荐 v1 收纳进 `projects/<id>/`（守「双根不许合一」铁律），外部任意目录注册留 v2（需过 FS 抽象层）。
- **验收**：真实项目跑通 init → index → 手改文件 → 增量 → RAG；全局 KB 零混入；增量编译不覆盖人工改卡。

### 需求 2 · 本地快诊断（类 jev / 参考 laya）

**目标**：完全本地算力的分层诊断——S 级确定性（零 token、<100ms）+ A 级 laya 学生头（本地 GPU），静默追写标红与 agent tool 双消费。

| # | 能力 | 现状锚点 | 要做什么 |
| --- | --- | --- | --- |
| 2.1 | S 级服务化 | quality-scan / prose-scan / zhuque-check 规则已有 | 脱离 agent 纯服务跑，常驻 + 统一出入口 |
| 2.2 | A 级学生头服务化 | laya-scan.py 批扫已验证 | **前置：环境回填**（venv + student-v3 权重）；批扫 → 常驻服务 + 按段落节流的增量接口 |
| 2.3 | 诊断契约 | 无 | `diagnosis-report.schema.json`：`evidence[]`（程序判定，有证据）与 `opinion{}`（模型观点，仅供参考）**硬分离**——信任机制地基 |
| 2.4 | 端点与 tool | verbs 单表 27 动词 | 诊断动词进 verbs（CLI/HTTP/MCP 三脸同源）；编辑器标红归宿主（与需求 3 同一立场）；幅度可配 = 规则子集 × 置信度阈值 × 严重度过滤 |
| 2.5 | 静默追写纪律 | laya「4B 永不兜底、学生不可用显式失败」纪律在案 | 延迟预算 S < 100ms、A 单段百 ms 级（按段落节流）；默认只标最高置信 1–2 条其余折叠；**绝不让大模型进静默链路** |

- **验收**：延迟/误报实测达标；断网全功能可用；agent 侧可调（去 AI 味 / 文风检测——`ai-trace` 条款已在家）。
- **非目标**：不做编辑器 UI；不做云诊断；B 级（主观审美）不进静默链路（决策点 D5）。

### 需求 3 · kit 不做前端（底座化）

**目标**：pi-web 演进线终止。kit 三输出——文档、自包含可视化 HTML、契约数据包；前端适配全交宿主。

| # | 能力 | 现状锚点 | 要做什么 |
| --- | --- | --- | --- |
| 3.1 | 立场入规格 | AGENTS.md 已有「前端已切离」但未成规格 | ARCHITECTURE.md 定「不做什么」；三输出交付形态 + 铁律（HTML 只读、零运行时依赖、不回 call kit） |
| 3.2 | 页面件补齐 | 世界书图谱 / 流程图 / journal 模板已有 | 补时间轴大事记整页、诊断报告页（依赖 2.3 契约）；模板独立成文件不进核心包 |
| 3.3 | 宿主接入固化 | **pinax-bridge 是活样板**（任务化接口/契约镜像/预算归属/工具环桥） | 提炼成 docs/integration 宿主篇；`tasks-bridge-*` 运行数据归位 |
| 3.4 | panel/kitapp 处置 | fork 已落库 10+ commit、七视图全实现 | 三选一：冻结保留 / 剥离出仓入 extracts / 仅留插件壳（决策点 D2）；无论如何停止新功能投入 |

- **验收**：宿主仅凭 docs + 契约 + 数据包可完成适配（pinax 实证可行）；HTML 双击打开、零外部请求。

### 需求 4 · 能力/知识分化 + 写诊改三相一体化

**目标**：规则从工具里搬进 KB，工具退化为执行器；写/诊/改共用一份规则定义，**结构上不可能矛盾**；「凡可被写的，都可被拆」。

| # | 能力 | 现状锚点 | 要做什么 |
| --- | --- | --- | --- |
| 4.1 | 规则 DSL 契约 | 无 schema | `rule.schema.json`：`rule_id / tier(S\|A\|B) / scope / 检测目标 / 判定逻辑 / 证据字段 / 严重度 / 修复策略 / provenance.refs` |
| 4.2 | 一源两视图 | **两本账**：knowledge/rules 17 卡 ↔ 扫描器条款（laya-ft/questions.spec.json 13 条 qid + quality-scan 规则） | 卡引用 qid、扫描器按卡执行；诊断视图（命中+证据）/ 建议视图（修复策略反向表达）/ 修改视图（自动应用，宿主确认） |
| 4.3 | 一次性工具归并 | `mf_analyze_curve` 写死在 agent.ts；module-lint 报 `render-prompt-seedance` 孤儿能力 | 泛化为「卡驱动诊断动词」`diag(dimension)`——一张规则卡即一个诊断能力，不再是每场景写一个 tool |
| 4.4 | 三相打通 | 无 | 诊=卡判定、建=修复策略反向表达、改=修复策略应用（可回滚）；三相一致性测试钉死「同卡诊/建/改不可能矛盾」 |
| 4.5 | 拆（逆向） | knowledge/deconstruct/ 空位已留 | `deconstruct.schema.json`；产物 = 带 provenance 的规则卡回流 KB；**抽样优先**，禁止「全书记忆化」冒充拆书 |

- **验收**：任一规则可答「哪一级 / 证据是什么 / 怎么改」；诊断与建议 100% 同源；拆出的规则可被诊复用。
- **分级判据**：S=可精确定义（确定性工具，零 token）；A=有模式需上下文（KB+本地学生头）；B=主观审美（只走 agent 评审通道，不进诊断服务）。
