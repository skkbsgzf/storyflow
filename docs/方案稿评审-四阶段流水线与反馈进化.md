# 方案稿评审：《写作 Harness 方案稿：四阶段流水线 + 反馈进化》

> 评审对象：用户提交的方案稿（选题 Research → 方案 Plan → 编剧 Script → 写作 Prose；每阶段以「上一阶段产物 + 世界模型」为输入，产出结构化本地文件并附验收标准；反馈以备注/diff 落盘，驱动**配置级进化**而非提示词漂移）。
> 评审基准：本仓 `docs/底座规格-miniflow-harness.md`（R4/R5 生效规范）＋ `AGENTS.md` 十一条铁律 ＋ 当前 HEAD 实际代码。
> 结论一句话：**方向对，且大部分已建成；三条与仓库法则冲突不可照写，两处真缺口值得吸收。**

## 一 · 逐条映射：方案稿概念 ↔ 仓库既有实现

| 方案稿 | 仓库现状 | 判定 |
| --- | --- | --- |
| 四阶段：选题 / 方案 / 编剧 / 写作 | `flow.stages` 段（段内节点组）＋ `stages/<id>/stage@1` 可复用包（已存在 4 个：topic-selection / polish / format-compliance / publish-review） | ⚠ **机制已有，形态要改**（见冲突 1） |
| 阶段产物 = 结构化 JSON（research-brief / chapter-plan / chapter-script） | 产物 = **md ＋ artifact@1 头部**（`contracts/artifact-header.schema.json`），索引落 `registry/artifacts.json` | ⚠ **形态冲突**（见冲突 2） |
| `acceptance_criteria`（含 `show_dont_tell_ratio_min: 0.7`、`dialogue_ratio_target: 0.35`） | `op.asserts` 三态裁决（`core/src/asserts.ts::runDeclaredAsserts` 单点派发；block / warn / unverified） | ⚠ **缺「数值目标」原语**（见缺口 1） |
| 人工只批 Plan 与 Prose | kit 边界门（`gate_role:"kit-boundary"`）是唯一人工点；`policy.kit_boundary ∈ {always,auto,off}` ＋ `suppress-boundary` 可调 | ✔ 一致（且**可调成全自动**），见下 |
| 反馈（备注 / diff）→ `ConfigEvolver` 提模式 → 进化配置 | **`core/src/optimize.ts` 已建成**：8 条规则、按 `kit.op` 维度生效、risk 分级、结构类补丁永不自动落地、落 `registry/optimize.json` | ✔ 一致（但**不得用 LLM 分类**，见冲突 3） |
| 「从修改点重跑」 | `state.nodes[id].stale` ＋ `flow_rerun`（重编译时受影响下游 pending＋stale） | ⚠ **粒度差异**：内核粒度 = node，非 stage |

### 关于「人工只在 kit 边界」的一个重要实测修正

方案稿把「Plan 强制人工、Prose 强制人工」写成硬约束。仓库的正确口径是：kit 边界门**是派生的、可调的**。验证层全自动重拍（`_918test`）正是靠 `flow_overlay` 设 `kit_boundary=off` ＋ `gate_mode=auto`，把全部门交卷自动过，才做到三项目无人值守跑到底。

⇒ **方案稿的「强制人工」必须落成 overlay 旋钮（默认 manual），不能硬编码进门。** 否则自动批量跑（本仓刚需：验证层重拍、benchmark 回归）全部被堵死。

### 关于「反馈进化」的一个关键澄清

`optimize.ts` 文件头已显式写明立场：

> 这是**确定性启发式**，不是 LLM。① 规则可审计：每条提案都带 metrics 证据（哪条指标、值多少、样本几条）；② 与内核同源：优化器能改的东西 = overlay 能表达的东西 = 面板能渲染的东西。
> agent 的角色是**使用**这些提案（挑哪条、为什么、批不批），而不是凭感觉重画流程图。

也就是说，方案稿要的 `ConfigEvolver` **已经以更严格的形态存在了**。它的输入是 `registry/metrics-summary.json`（上下文命中率 ＋ tool 效率），输出是 overlay patch 提案，结构类补丁（`place-node/remove-node/set-op/add-edge/set-edge/remove-edge`）**无论如何都不自动落地**。

## 二 · 三处冲突（照写会破法规 / 破链）

### 冲突 1：不能「一个阶段一个 flow / 一个项目」

`flows/README.md` 明文：

> **flow = 一条端到端生产线**（有独立交付物）；stage 是 flow 内部的段落，验收门是段落间的关卡。**不为一个 stage 单开 flow**；
> 可复用能力段封装为 **Stage 包**（`stages/<id>/`，stage@1）…… flow = Stage 拼接，**不为 Stage 单开 flow**。

仓库的真实切法在 `projects/` 里可以直接看到：**一条 flow 一个冒烟项目**（`p-ccwdl-topic→topic-selection`、`p-ccwdl-outline→outline-production`、`p-ccwdl-ep→episode-script`、`p-ccwdl-long→novel-longform`、`p-ccwdl-fq→novel-fanqie`、`p-ccwdl-prose→novel-prose`、`p-ccwdl-decon→book-deconstruct`），**不是一阶段一项目**。

⇒ 四阶段应表达为**同一条 flow 内的 `stages` 段** ＋ 需要复用时抽成 `stages/<id>/stage@1` 包。

### 冲突 2：阶段产物不宜改成结构化 JSON

现行产物模型是 **md 正文 ＋ YAML-ish artifact@1 头部**（九项必填 ＋ `review{}`），版本/上游/审核背景一律归头部，正文只放内容。这条链上挂着：`artifact-lint`（7 projects / 295 md）、`page-lint`（44 条契约断言）、交付清单核对、`upstream` sha 命中率分子。

⇒ 若每阶段改吐 JSON，会同时打断上述四处，并丢掉「人可以直接改稿」这一方案稿自己主张的性质。**需要结构化字段就进头部；需要派生读模型就落 `registry/*.json`（R5「派生只算一次」纪律）**，不要新增平行真源。

### 冲突 3：反馈进化不得引 LLM 做模式归类

方案稿的「`PatternBasedEvolver`：prose 类『sensory 不足』出现 ≥3 次 → 追加规则 `min_sensory_per_beat: 2`」——**目标方向完全正确**（这正是 tool 内容配置旋钮该干的事），但**归类环节若交给 LLM 就踩两条红线**：

- `optimize.ts` 已声明「不是 LLM」；
- WO-A 红线「**禁止引 LLM 当机器校验器**」。

⇒ 「出现 ≥N 次」这类**计数必须是确定性的**（对结构化反馈字段计数，不是对自然语言语义归类）；LLM 只能在「人/agent 读提案并决定批不批」这一层出现，且结构类改动永远人批（铁律 4）。

## 三 · 两处真缺口（值得吸收）

### 缺口 1：`acceptance_criteria` 的数值质量线——**全仓不存在**

全仓 grep `acceptance_criteria` 零命中。现有断言是「能正则判定的二元 / 同族匹配」形态，**没有「数值目标 ＋ 容差」这一原语**。

方案稿给的例子恰恰是最有价值的部分：

```
show_dont_tell_ratio_min: 0.7
dialogue_ratio_target: 0.35
```

这类指标有三个别的断言做不到的好处：① 可累积统计（跨章看趋势，不是单点过/不过）；② 天然适合当优化器的证据（数值 + 样本数）；③ 可作软信号（偏离目标但不 block）。

⇒ **正确的落点是 kit op 级的新断言种类**，四环一次到位（否则会重演「声明了但没人跑」）：

1. 声明：`kits/<kit>/kit.json` 的 `ops.<op>.asserts` 登记；
2. 执行：`core/src/asserts.ts::runDeclaredAsserts` 增加数值比较分支（**禁止另起一套**）；
3. 可见：`kits/*/kit.json` 的 `config` 旋钮表 ＋ 面板 `configPaper` 展示（改阈值不用改代码）；
4. 校验：`tools/kit-lint.py` 增规则（阈值缺失 / 无实现 / 未登记断言）。

### 缺口 2：反馈进化的**前置**是指标口径，而口径当前是失真的

`docs/_918test-自检报告.md` 已在真运行中量化出三处失真：

1. **标尺卡命中率恒 0%**：submit 侧 `ctx.ids` 不含派发阶段注入的标尺卡 → 分子被系统性低估（`plot.plot-redline` 显示「注入 28–58 张、只用 5–6 张」，其中至少一部分是口径造成的假象）；
2. **glob 模式污染分母**：`kb/trope/*` 这类声明被展开后计入未命中；
3. **重试计入 submits**：单次产物重交被算成多次派发。

另有已修但值得并列的一条：成本口径里的 `assertBlock×5` 溢价在修复前**恒为 0**（`asserts:{pass:problems.length, block:0}`），「被高频打回的 tool」在指标里根本看不见。

⇒ **顺序不能反**：`ConfigEvolver` 的输入就是这张指标表。口径不修，进化器会稳定地优化噪声。这正是本项目已记录在案的模式——**「指标撒谎 → 优化器瞎」**。

## 四 · 建议执行顺序

| 优先级 | 事 | 理由 |
| --- | --- | --- |
| **P0** | 修指标口径 **D1–D5**（对应 `_918test` 报告拍板清单） | 纯增量、零依赖、证据已在手；**反馈进化的唯一前置**，不做则后面全白做 |
| **P1** | 把 `acceptance_criteria` 落成 kit 级「数值断言」原语（四环齐全） | 方案稿唯一真新增价值；且顺带补上「断言只验能正则判的东西」这一结构性短板 |
| **P2** | 阶段粒度对齐：确认 `flow.stages` ↔ `stages/<id>/stage@1` 关系，给 stage 包补 **stage-lint** ＋ 迁移到 flow@2 词表 | 现状 `stages/topic-selection/stage.json` 内部仍是 flow@1 词表（`skill`/`file`/`transform`），且**不在任何门禁里**——典型「声明了但无人校验」 |

### 明确不建议做的事

- 按方案稿拆成四个 flow / 四个项目（破命名法）；
- 每阶段改吐结构化 JSON（破 artifact/page 两条链）；
- 用 LLM 对自然语言反馈做语义归类来驱动配置（踩红线）。

### 关于「要不要现在细化某一阶段的 prompt 设计」

**暂不细化。** 阶段间交接契约（产物形态、验收原语、指标口径）尚未冻结，此时写阶段 prompt 等于给流沙浇水泥——冻结后大概率整体重写。建议 P0/P1 落地、契约冻结后再做，届时 prompt 只需围绕**已确定的数值目标**来写，反而更省。
