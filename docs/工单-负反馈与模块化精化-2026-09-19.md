## 工单

### W-01 模块职责三件套的声明式契约（module@2）｜建议优先级 P0
- **需求**：模块在设计之初明确 输入职责/输出职责/验收职责，由 schema 冻结、lint 强制、前端展示。
- **现状**：三件套散落三处——输入在 op.desc 文字里；输出在 flow.outputs + op.output；验收在 op.asserts。
  module-lint 无法校验「一个模块是否声明了完整职责链」，前端也没有职责卡。
- **建议**：module@2 增 `io: { input: {from: flow-input|<module>, shape}, output: {file, audience}, acceptance: [assertId…] }`；
  module-lint E 级强制；expandFlow3 传播进 effective@2；前端模块卡片直接渲染职责三件套。
- **影响面**：contracts/module.schema.json、module-lint、modules.ts、8 个 module.json、前端模块卡。

### W-02 产物可见性分级（交付件 vs 过程件）｜P0
- **需求**：用户只看每模块一份成熟交付；过程件（乱的分析/思维链痕迹）默认折叠。
- **现状**：前端按目录前缀猜（对外交付/内部/过程文件），R6 模块目录（01-选题/ 等）内全部平铺成
  「过程文件」，交付件与过程件混排——你实测「看不懂乱的分析」的直接来源。
- **建议**：artifact class 声明制——flow.outputs / module io 指定的产物标 `deliverable`，其余模块目录内
  产物标 `process`；文件架默认只开交付件层，过程件收进「模块内幕」折叠区（点开才见）。
- **影响面**：assembler（header class）、registry、project-pages payload、模板文件架/产物管理。

### W-03 剧本 IR 的 schema 化（超越文本层校验）｜P1
- **需求**：剧本是「更优的格式化数据」——现在它只是 markdown 约定格式，AE-SCRIPT-FIELDS 是正则启发式
  （字段在不在，不管内容对不对）；ghostwrite 消费的也只是文本。
- **建议**：剧本 frontmatter 携带 JSON 结构（scenes[]：who/when/where/what/why/how/action/value/hook/
  dialogue[]），渲染层由结构生成 markdown 人读视图；校验器从正则升级为 schema 校验；ghostwrite 可
  机读结构化输入（伏笔台账/知情范围自动进 continuity 台账，免人工登记）。
- **影响面**：script-forge/ghostwrite 两个 skill、新 script.schema.json、aesthetic.ts、连续性台账接线。

### W-04 模块级结果报告读模型（module-report@1）｜P1
- **需求**：负反馈第一步——每次跑完，用户拿到**每个 module 的结果报告**进行批注/修改。
- **现状**：只有全项目 metrics-summary（节点粒度）；模块收口时的产出清单/验收三态/命中率/耗时/打回史
  要人从 journal 里翻。
- **建议**：内核在模块收口（link 通过）时生成 `registry/module-report-<mid>.json`：产出物+验收三态+
  ctx 命中率+耗时+重试史+上游依赖指纹；前端模块卡片直接挂报告入口与批注框。
- **影响面**：kernel（advance 的 link 分支）、新读模型 schema、前端模块卡。

### W-05 提示词 patch 通道（skill 层 overlay）｜P1
- **需求**：负反馈的 agent 优化对象包括「提示词」——现在 overlay 只能改 config/knowledge/asserts，
  skill 提示词文本动不了；agent 说「我会改提示词」是空话。
- **建议**：skill 文本版本化（skills/<name>.md 加 version + skills-overlay：<module>.<op> 的 patch 补丁层，
  结构同 flow-overlay：proposed→applied），module-lint 校验补丁可应用；提示词改动永远进拍板清单。
- **影响面**：skills 目录结构、新 overlay 类型、内核 buildTaskPackage 装载点、审计日志。

### W-06 负反馈自动触发与批注接线｜P2
- **需求**：跑完自动出报告→用户批注→agent 自动拆解为 tool 参数/顺序/流程/提示词的优化提案。
- **现状**：orchestration-miner 要人手动跑；前端批注导出（批注与意见.json）与 flow_optimize 的 evidence
  没有接线；提案池与批注是两个孤岛。
- **建议**：① run completed 后内核自动调 flow_mine（组装证据包）产出 findings；② 前端批注提交时
  直写 optimize 提案池（origin=user，status=proposed）；③ flow_optimize 合并 findings+批注出 patch 提案，
  用户在页面上逐条批（批准/驳回），批准的 overlay 结构类自动落，非结构类进 set-tool。
- **影响面**：kernel（completed 钩子）、前端批注面板、flow_optimize 证据合并逻辑。
