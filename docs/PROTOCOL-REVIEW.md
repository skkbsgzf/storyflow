# 审核接入协议（PROTOCOL-REVIEW）· v0.8

**立场**：StoryFlow 运行时**不提供**审核、打回、红队、合规裁决——宿主系统（把它嵌进自己产品的平台方）
自己编写这些逻辑。本协议只定义宿主如何把**自己的审核**接到我们的运行时上。

## 为什么运行时不含审核

- 同一套运行时，不同宿主的审核标准完全不同（平台合规 / 编辑部口味 / 个人偏好）——内置任何一种都是对其余宿主的强加。
- 内置审核层曾被实测证明会自我循环（判官过敏→回喂→过拟合），语义裁决的质量上限永远在宿主的模型与流程，不在运行时。

## 宿主接入审核的三条通道

### 通道 1 · gate 暂停点（推荐）

flow 里保留 `gate` 机制：节点交卷后运行时**暂停并等待宿主裁决**，宿主通过动词代理放行或打回：

```
运行时：节点完成 → status=awaiting(gate)
宿主：轮询 GET /status（或订阅 /events 的 gate 事件）→ 自己跑审核 → 裁决
宿主：POST /api/kernel-verb { verb:"flow_gate", args:{ project, pass|reject, comment } }
```

gate 不内置任何裁决逻辑——它只是「暂停 + 等待」这个协议动作。

### 通道 2 · 事后审（产物面）

宿主对已落盘产物自行审（读 `/api/panel/files` 或直接读磁盘），不合格就调
`POST /api/kernel-verb { verb:"flow_rerun", args:{ project, node } }` 定点重跑该节点。

### 通道 3 · 对话内审核（agent 面）

宿主的审核 agent 通过对话 API 参与同一会话（`POST .../turn`，mode=plan 只读档），
产出审核意见——要不要采纳仍由宿主业务层决定。

## 明确不提供的

- 内置判官 / 打分器 / 红队题库（v0.8 已整体移除，含 laya 学生接线和回喂链路）
- 提交内容的语义拦截（运行时只做确定性完整性：文件存在、头部字段、产物计数——防事故不防观点）
- 审核标准配置项（审核标准在宿主，不在配置文件）

## 兼容性承诺

gate / rerun / 会话 API 三者的请求与响应形状属于**稳定面**：变更只增不改名；
破坏性变更升大版本并在 CHANGELOG 顶部声明。
