> 仓库 `D:\storymasterv4` ｜ 方法：四路并行只读审计（阻塞机制 / 硬编码约束 / 可移植性 / 初始化路径）+ 关键结论逐一亲自复核。

## 二 · 通道类：「声明了却不生效」—— 比"缺失"更危险

### 1. **两套 overlay 词汇表，交集只有 `set-policy`**（本次审计的头号结构问题）

| | `overlay.ts:36-43` + `contracts/flow-overlay.schema.json` | `modules.ts::effectiveFlow3`（`kernel.ts:156` 调用） |
|---|---|---|
| kinds | `set-node` `set-op` `place-node` `remove-node` `set-edge` `add-edge` `remove-edge` `set-tool` `set-policy` `suppress-boundary` `set-input`（**11 种**） | `set-policy` `set-module` `insert-tool`（**3 种**） |
| 交集 | —— 只有 **`set-policy`** —— | |

**而且**：`set-module` / `insert-tool` **不在 schema 里**（实测 schema 枚举无此二项），却**在 flow@3 展开器里被实现**（`modules.ts:362,369`）。
⇒ **契约、实现、文档三方各说各话。** 后果：`set-tool`（唯一能改 tool config / `model_tier` 的）**在 flow@3 的模块展开路径上不被读取**；`set-module`/`insert-tool` 反过来不在契约里。
**旁证（最具说服力）**：`p-wxl-001` 的运行者——**写这套系统的人**——在自己的决策文档里断言「overlay 通道只有 set-policy/set-module/insert-tool，无 set-tool.config」。**连作者都分不清哪条通道能用。**

→ **处置 A**：统一为一套词汇表，schema 与实现互相对齐；新增 lint：**任何一个 patch kind 必须至少有一个消费者实现**。

### 2. **前端让用户生成 schema 里不存在的 patch**
`tools/workflow-page-template.html:1316` 文案：「勾选能力 → 生成 `set-module caps` / `insert-tool` overlay patch」。
→ **处置 A**。

### 3. **工具箱抽屉是只读的，却在文案里说"勾选即出 patch"**
`openToolboxPaper`（`workflow-page-template.html:1297-1318`）：`cursor:default`（`:1310`）、**无任何事件绑定、没有 checkbox、不生成任何 patch**；而 chip 写着「勾选即出 overlay patch」。
→ **处置 B** —— **这恰恰是初始化面板要复用的机制**：真正实现「勾选 → 生成 patch → 人确认 → 落盘」。

### 4. **`项目配置` 编辑器恒显占位（唯一配置 UI 是坏的）**
模板 `:1555` 读 `DATA.projectConfig`，但 `tools/project-pages.py:378-394` 的 payload **未注入该键**（实测 grep 只在模板命中）。
→ **处置 B**：注入现值。

### 5. **optimizer 产出内核不认的 patch**
`optimize.ts:251` 生成 `set-policy {key:"kit_boundary", value:"auto"}`；而 `types.ts:117` 已声明 `kit_boundary` 在 R6 **退役**，`modules.ts:356-360` 只接受 `key==="link_default"` ⇒ **静默丢弃**。
→ **处置 A**。

### 6. **断言路由靠文件名正则，改名即静默失效**
`aesthetic.ts:487` 的 `/章节正文|第\d+章|正文|终稿/` 决定是否走 488 分支；而 `chapterLengthAssert` 的**唯一调用点**在 `:602`（488 的提前 return 之外）。
实测后果（上一轮已验）：`AE-CH-LEN` 恒不执行；`03-写作/prose-assembler.md` 文件名不匹配 → 掉进 `:495 AE-SKIP-NON-BEAT`，**其声明的 5 条断言全部恒废**。
→ **处置 A**：改由**节点契约**（op / io.output 职责）路由；lint 增「声明的断言在本产物类型下不可达 = error」。

### 7. **`minitool.timeoutMs` 声明无消费者**
`contracts/minitool.schema.json:20`（60000），内核从未读取。
→ **处置 A/B**。

## 六 · 初始化面板：现状与应然（回答"至少在初始化时给面板"）

### 现状（实测）
- 建项目：CLI `flow_run`（`cli.ts:83`）/ `flow_init`（`cli.ts:105`）/ `tools/project-init.py:79-126`；**MCP 有 7 个 verb 却没有 `flow_init`**。
- `flow.inputs` 声明很完整（`project|string|number|boolean|enum` + `required/default/options`），消费于 `cond.ts:169 resolveInputs` → `state.inputs`。
- HTML：**无 `<form>`、无 checkbox**；可编辑的只有原始 JSON textarea（`:1555-1570`）和技能编辑；而 `projectConfig` 还没注入。
- **所有 `flow.inputs` 字段都没有逐字段表单** —— 用户只能手写 JSON。

### 应然：四分区，数据全部来自**已有声明**（不新增契约）
1. **项目输入区** —— 读 `flow.inputs` 逐字段渲染（required 校验 / enum 下拉 / number 默认值），写回 `项目配置.json`。**这一区能直接消灭"手写 JSON"和"没有 flow_init 的 MCP"两个缺口。**
2. **编排区** —— 读 `module.caps` / `skeleton` / `also_fits` 渲染勾选（复用工具箱抽屉，但**要真的能勾**），生成 patch 前先做 **kind 白名单校验**（对齐第一节修好的 schema）。
3. **阈值与预算区** —— 把第三节那批「引擎内常量」提升为「出厂默认 + 项目可覆盖」，按常用/高级分组。
4. **门与风险区** —— 第一节那些"卡住"的旋钮：`itb-` 默认策略、link 默认、**最大重跑轮次**、**等待超时**。

> 这样处理正好落在用户要求的那句：「一些可能阻塞项目的约束要全部剔除，**或者至少在项目初始化时，生成对应的项目初始化面板，在 HTML 上供用户填写**」——凡是**不该由代码替用户拍板**的（模型档位、成本上限、人工门密度、重跑上限），从硬编码变成面板字段；凡是**纯负债**的（死配置、无消费者的声明、schema 外的 kind、越权的静默丢弃），直接剔除。
