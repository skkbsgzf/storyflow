# 版本宣告 · miniflow harness v4.0.0（协议基线 + 老格式处决清单）

> 生效：2026-09-21 ｜ tag：`v4.0.0` ｜ 事实源：仓库根 `VERSION` + `CHANGELOG.md`
> 背景：git 断链整并落定（`docs/事故-2026-09-18-git目录误删与恢复.md` §七）＋ R8-S1..S4 已入库（本宣告落笔时 tip = R8-S4b）。

## 一 · 为什么是 4.0.0

仓库本代即 storymaster-**v4**；harness 此前从未有过全局版本（唯一指纹是 dist 目录名 `release-<sha>-dirty-<date>`），文档代际 R1..R8 只覆盖规范演进，契约 `@N` 只覆盖单 schema 兼容性。**v4.0.0 = 首个受治理的产品版本**：从此「用户可见里程碑 = VERSION 升档 + CHANGELOG 一条 + git tag」。它与契约代数不同轴：`@N` 管兼容性，semver 管发布节奏，两者并行不混用。

## 三 · 即刻生效的规则

1. 新建/修改 flow 只允许 flow@3；flow@1/@2 **只读**——不再新建项目绑定、不修非安全类 bug，要动先迁移（工单批A）。
2. 迁移完成前 `flow-lint` 对 flow@2 存量保持放行（仅提示）；批A落地、升 **v4.1.0** 时收紧为硬拒。
3. kit@1 只读：新能力一律入 `modules/`；kit-lint 现有「只提示迁移」口径维持至工单批D。**（批D 已完成，v4.2.0：`kits/` 目录与三个 kit 迁移器已删除，kit-lint 事实源切 `modules/*/module.json` 并转阻断门禁——本条规则随批D 生效并闭合。）**
4. `docs/底座规格-miniflow-harness.md` 等历史规格中的旧口径以本宣告为准（冲突处已就地标注 v4.0 注）。
5. R 代际（R1..R8）归档为历史命名；后续发布治理一律走 VERSION/CHANGELOG/tag（规范文档文件名可沿用旧惯例，但「发版」以版本号为准）。
